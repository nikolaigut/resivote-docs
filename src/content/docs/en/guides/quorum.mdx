ResiVote calculates quorums according to Swiss property law (ZGB). Resolution capability is tracked live during the meeting and frozen as a snapshot when an agenda item is opened.

## Quorum Types

Each agenda item defines its quorum type:

| Type | Meaning | Legal Basis |
|-----|-----------|-----------------|
| Simple majority | Yes > 50% of present head votes. Abstentions and uncast votes count as implicit no. | — |
| Qualified majority | Yes > 50% of present owners (heads) **and** > 50% of **all** eligible value quotas. | Art. 647b/d/e, 712g para. 3 ZGB |
| Unanimous | 100% of **all** registered owners (heads) and value quotas must vote yes. Absences without a positive proxy count as no. | Art. 647e ZGB |
| Absolute majority | Yes > 50% of **all** registered owners (regardless of attendance). | — |
| Custom | Yes >= custom percentage of the configured basis. | Regulations |

### Custom Quorum

For custom quorums, the agenda item holds three settings:

- **Threshold** – threshold in % (e.g. 66.67)
- **Value quota threshold** – optional separate threshold for value quotas
- **Basis** – present or all eligible

### Quorum Override

The chair can lift a quorum block. The agenda item holds:

- **Quorum override** – when enabled, votes are accepted even if the quorum was not met when the agenda item was opened.
- **Override reason** – mandatory reason text when the override is enabled.

The system checks before each vote: if no snapshot exists, the check is skipped. If the quorum was not met and no override is set, the vote is rejected.

## Quorum Calculation

The quorum engine is the core component for vote evaluation. It calculates a result per community and aggregates them into an overall result.

### Inputs

- Agenda item with quorum type and custom settings
- Communities of the meeting
- Units and ownership shares
- Attendances
- Proxies
- Cast votes

### Outputs per Community

| Field | Meaning |
|------|-----------|
| Yes / no / abstain head votes | Head votes |
| Yes / no / abstain value quotas | Value quotas |
| Head vote threshold / value threshold | Required yes votes |
| Head vote passed / value vote passed | Whether threshold was met |
| Passed | Overall result (empty for informational agenda items) |
| Voting rights cap applied / capped owners | Voting rights cap applied |
| No-voters / abstain voters | Last names of no/abstain voters (for minutes) |
| Candidate tally / winner | Election result |
| Informational | No yes/no result (e.g. free text) |
| Inherited | MEG result inherited from linked STWEGs |

### Defensive Normalization

The quorum engine normalizes inputs defensively: empty communities produce an informational result, missing votes count as implicit no, and rounding errors are absorbed.

### Overall Result

The overall result is positive when **all** communities meet the quorum. Inherited MEG results are not double-counted.

## Live Quorum

The live quorum engine answers the question "is the meeting capable of passing resolutions?" in real time, based on current presence — independent of cast votes.

### Resolution Capability

The meeting is capable of passing resolutions when **more than half** of the head votes **and** more than half of the value quotas are present/represented, plus the minimum number of owners. "More than half" is a **strict** inequality: for an even total N, the threshold is `N/2 + 1` (e.g. 4 owners → 3 required). Exactly 50% is not sufficient.

### Voting Rights Models

Which conditions apply depends on the community's voting rights model:

| Model | Head Condition | Value Quota Condition |
|--------|---------------|---------------------|
| Head and value / custom shares | yes | yes |
| Head only | yes | skipped |
| Value only | skipped | yes |

### Output

Per community, the live quorum engine reports:

- Head quorum met, value quorum met, minimum owners met, overall quorum met
- Required head votes, required value quota
- Missing head votes, missing value quota, missing owners

The quorum is reached when all communities meet the quorum.

## Presence Calculation

The system collects attendances, proxies, and ownership shares and aggregates them into community-scoped snapshots. This presence source is shared between the live quorum engine and the API, so both use the same data.

### Process

```d2
direction: right
Communities: load
Attendances: load
"Proxies": load
Mappings: "Unit → Attendance\nUnit → Proxy"
"Per community": "Load units\nSum shares\nCalculate head & value"

Communities -> Mappings
Attendances -> Mappings
"Proxies" -> Mappings
Mappings -> "Per community"
```

<Steps>
  1. **Load communities** – all communities of the meeting.
  2. **Load attendances** – all attendance records of the meeting.
  3. **Load proxies** – all proxy records of the meeting.
  4. **Build lookup maps** – map units to attendances and active proxies.
  5. **Aggregate per community** – for each community: load units, sum ownership shares, calculate present/represented head votes and value quotas.
</Steps>

### Presence Status

Each owner receives a presence status:

| Status | Meaning |
|--------|-----------|
| Present | Owner is present (check-in completed) |
| Represented | Owner is represented by a proxy |
| Absent | Owner is absent |

The community snapshot summarizes: total owners, total head votes, total value quota, present owners, present head votes, present value quota, and attendance percentages for both head votes and value quotas.

### Proxies

An owner can authorize another person as a proxy. The system checks:

- Only the proxy may vote digitally, not the grantor.
- The proxy must cover the agenda item.
- Instructed votes must match the instruction.

## Quorum Snapshots

When an agenda item is opened, the current presence and quorum status are frozen as a snapshot. The snapshot serves as the quorum basis for that agenda item.

### Persistence

The snapshot is stored in the database and survives server restarts. It is the basis for the vote validation check.

## Community Types and Standards

### STWEG vs MEG

ResiVote distinguishes two community types:

| Type | Meaning | Default Quorum (Head/Value/Min Owners) |
|-----|-----------|---------------------------------------|
| STWEG | Condominium owners' association | 50% / 50% / 2 |
| MEG | Co-owners' association | 50% / 50% / 1 |

The defaults can be overridden by regulation fields when they are set.

### Voting Rights Models

| Model | Description |
|--------|-------------|
| Head and value | Head votes + value quotas (STWEG standard) |
| Head only | Head votes only (1 unit = 1 vote) |
| Value only | Value quotas only |
| Custom shares | Custom shares per unit (MEG-specific) |

### MEG Inherits Owners from STWEG

A MEG can inherit owners from linked STWEGs:

- **Inheritance** – only relevant for MEG. When enabled, the MEG does not manage its own units/owners but inherits them from linked STWEGs.
- Inheritance only applies when the MEG has no own units. This prevents double counting.
- The link between STWEGs and MEGs is managed as a many-to-many relationship.

Inherited MEG results are marked as inherited and are not double-counted in the overall result.

### Developments

A development groups multiple communities (STWEG and/or MEG). A meeting can span multiple communities of a development.
